## Objective

Rename the **command names and internal identifiers** that still say `cortex` to `rapso`, in the
three files whose *filenames* define the user-visible `/cortex-init` command and the sync entry
point, plus the two references and the one defect-payload key that point at them.

This is **Bucket 3** of the Cortex → Rapsodia rename, explicitly deferred by `rename-rapsodia-repo`
("changes an API, not prose") and left untouched by `rename-rapsodia-residual-prose`.

## Why it is its own change

The filenames are not prose. `commands/cortex-init.md` is the file that defines the `/cortex-init`
command name, and `cortex-init.sh` copies it into `$GLOBAL_CMD_DIR` and every project's
`.opencode/commands/`. Renaming them renames an **API**, so it needs its own reviewable unit and its
own decision — which is what this change is.

## Decision taken

Clean rename, no compatibility alias. The consumer projects have **not** been synced under the new
brand yet (that sync is the step after this change), so no external consumer depends on the `rapso`
command name existing, and none has a reason to keep `/cortex-init` working. Bucket 4 is where
deliberate compatibility lives; these are not persisted matching keys.

## Risks and observed findings

1. **Installed commands are not deleted by the installer.** `rapso-init.sh` copies
   `rapso-init.md` into `.opencode/commands/` but never removes a pre-existing `cortex-init.md`.
   After this rename lands, any of the ~10 projects that already ran the old script keeps a stale
   `/cortex-init` alongside the new `/rapso-init`. This is the same class of bug as the sync that
   never deletes stale skills (observed 2026-09-18, Engram #4159). **Not fixed here** — it is
   consumer-side migration work that belongs with the sync step, and fixing it would exceed the
   rename mandate. Recorded so the sync step inherits it.
2. **`cortexVersion` appears in already-filed defect reports.** No surface in this repository parses
   it back (verified: the only match is the writer at `defect.ts:48`), and no `.github` issue
   template or installed skill reads it. Historical reports keep the old key; that is a record, not a
   matcher.
3. **Observed, not introduced, out of scope:** in `cortex-init.sh` the summary at L281 reads
   `$MCP_FILE`, which is only assigned inside the `else` branch of the `CORTEX_WORKTREE_PROVISION`
   guard (L99). Under `set -u` that path would fail on an unbound variable. The rename preserves the
   behavior exactly; it is reported, not repaired, because that would be a behavior change outside
   the mandate.
4. **Observed, not introduced, out of scope:** the hand-written `.atl/skill-registry.md` block
   (L196–231) is dead when `gentle-ai` is installed — L234–237 immediately regenerates the file and
   clobbers it. Confirmed by the smoke run: the final header is gentle-ai's
   `# Skill Registry — bucket3-smoke`, not the script's. A ponytail finding for the human, not a
   rename edit.
5. **BLOCKER — gga rejects the `defect.ts` rename on a pre-existing defect (2026-09-18).** The
   pre-commit hook reviews staged `*.ts`, and on this **one-line rename** it returned
   `STATUS: FAILED` against `cli/src/utils/defect.ts:28–37, 49, 54`, with violations unrelated to the
   rename. The finding is **real and pre-existing**: `scrubToken` (L20–33) returns any
   whitespace-delimited token unchanged when it matches none of its rules, and `scrubUrl` (L14–18)
   only strips a scheme URL's query. Consequences, read from the source: `--token=secret` survives
   verbatim; the token after `Authorization: Bearer` survives; `file:///abs/path` matches
   `HAS_SCHEME` (L12) and is then returned practically untouched. All three reach a payload the
   report string calls "already scrubbed".
   **Resolved by separation (human decision, 2026-09-18):** the file was reverted to base and both
   items moved to their own change. See ## Deferred to a follow-up change.
