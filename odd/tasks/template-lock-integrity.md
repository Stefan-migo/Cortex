# ODD Tasks — template-lock-integrity

Worktree: `/home/stefan/Cortex-odd-template-lock-integrity`
Branch: `odd/template-lock-integrity`
Base: `038d739` (main, after PR #14)

## Objective

Make the files `cortex init` and `cortex adopt` install actually installable, and make
`cortex worktree create` succeed in a project that Cortex itself created.

## Problem

The CLI template ships dependency lockfiles that are **not real lockfiles**. They are
hand-written stubs carrying a **fabricated integrity hash**:

```json
"integrity": "sha512-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
```

`npm ci` rejects them. `provisionWorktree` copies them into every new worktree and runs
`npm ci` without a try/catch, so **`cortex worktree create` fails on every project created
by `cortex init`**.

## Why

The worktree flow is the core of ODD. It was validated from inside the Cortex repository,
whose own lockfiles are real (generated by real `npm install` runs). The defect is
invisible from inside Cortex and visible from any freshly created project — which is
exactly where a new user starts.

## Findings

Numbering follows the original triage. B4 is the critical one.

### B4 — Forged template lockfiles (CRITICAL, blocks worktrees)

- `cli/src/template/.opencode/package-lock.json` — 12 lines, no `packages[""]` root entry,
  fabricated `sha512-xxx...` integrity.
- `cli/src/template/.opencode/tools/package-lock.json` — 10 lines, no root entry, no
  integrity, no transitive tree.
- `installDependencies()` (`cli/src/engine/worktree.ts:168-172`) runs `npm ci` whenever both
  `package.json` and `package-lock.json` exist. There is no fallback and no try/catch.
- `provisionWorktree()` (`:203-208`) copies both lockfiles **from the main worktree** into
  the new worktree, so the stub travels with it.
- `copyTemplate()` (`cli/src/engine/template.ts:55-75`) overwrites template files
  unconditionally, so `cortex init` writes the stubs even over a real lockfile.
- `cortex worktree create` does roll back cleanly on failure: no leftover worktree, branch,
  or directory (`cli/src/commands/worktree.ts:25-37`). The failure is loud and clean, but it
  is still a failure.

### B2 — Stale plugin pin

- Template `.opencode/package.json` and Cortex's own `.opencode/package.json` both pin
  `@opencode-ai/plugin@1.14.41` (added 2026-05-08, `2468f03`).
- The installed OpenCode runtime is `1.18.31`.
- `provisionWorktree():203` copies Cortex's pin into every worktree, so the staleness
  propagates. It does not break today (a worktree mirrors main exactly), but it means every
  worktree resolves a four-month-old plugin SDK.
- B2 and B4 are coupled: choosing a lockfile strategy forces a decision about the pin.

### B1 — `.opencode/plugins/**` ownership conflict

- `OWNED_PATHS` (`cli/src/engine/adopt.ts:7-11`) claims `.opencode/plugins/**` as Cortex-owned.
- The template ships a deliberate 6-line stub whose own comment says
  `Full plugin: install via 'graphify install --platform opencode'`.
- `graphify` is installed at `/home/stefan/.local/bin/graphify` and writes the real 30-line
  plugin (including the PowerShell `;`-vs-`&&` fix from #1646).
- Cortex therefore claims ownership of a file that another tool maintains and that Cortex
  deliberately does not ship. `--yes`, `--force`, or `update` replaces the real plugin with
  the stub.
- Verified on `lumat-agent`: its real plugin survived only because the adoption ran without
  `--yes`, which routes conflicting files to `skipped`.

### B3 — `mergeJson` duplicates the plugin entry

- `mergeJson` (`cli/src/engine/adopt.ts:72-76`) builds an **absolute** plugin path and guards
  with `includes()`, which compares exact strings. A project declaring the **relative** form
  gets the absolute form pushed alongside it:

  ```json
  "plugin": [
    ".opencode/plugins/graphify.js",
    "/home/stefan/repos/lumat-agent/.opencode/plugins/graphify.js"
  ]
  ```

- The relative form is canonical: Cortex's own `.opencode/opencode.json` and the template's
  both use it. The absolute form is also machine-specific and breaks on any other machine.
- Same function re-serializes with `JSON.stringify`, churning the project's own formatting.
- Root cause: `mergeJson` reads the template from `join(templateDir, 'opencode.json')` — the
  root config, which has no `plugin` key — so it never learns the relative convention.

## Decisions

### D01 — Lockfile strategy (answers T01)

**Decision: ship `package.json` only. No lockfile in the template. The install step becomes
adaptive.**

- Ship no lockfile for either `.opencode/` or `.opencode/tools/`.
- Both template `package.json` files declare `"@opencode-ai/plugin": "latest"` — which
  `.opencode/tools/package.json` already does. One declaration, no second convention.
- `installDependencies()` becomes: `package.json` present and lock present → `npm ci`;
  present without lock → `npm install`; neither → skip. Today the second and third cases are
  both a silent no-op, which is how a fresh project ends up with no resolvable
  `@opencode-ai/plugin`.

**Why not ship real generated lockfiles (option a)**

- A committed lockfile cannot stay current: it is generated once and rots. That is B2 — the
  pin and its lock went stale for four months in the template and in Cortex itself. Shipping
  a freshly generated lock resets that clock and does nothing else.
- There is no authoritative source to regenerate from. Cortex's own `.opencode/package.json`
  and both `.opencode/` lockfiles are **untracked local state**; a fresh clone has only
  `.opencode/tools/package.json`. The template's lock was hand-forged because there was
  nothing real to copy. Option (a) would need a maintenance ritual with no owner and no
  failure signal when it lapses.
- `@opencode-ai/plugin` is a runtime SDK for a user's project harness, not a build artifact.
  Following the installed runtime is worth more than freezing a version.

**Known limitation, accepted**

The plugin version follows the registry's `latest`, not the locally installed runtime. A
plugin published ahead of a user's runtime could diverge. This is already true of the
tracked `.opencode/tools/package.json`, and it does not break in practice: the template and
Cortex both run `1.14.41` against runtime `1.18.31` with all three tools working. Pinning to
the runtime would mean reading the runtime version at install time — new machinery for a
problem that has not been observed.

## New finding (B5, out of scope)

Nothing installs `.opencode/` dependencies on the normal path. `cortex install` only checks
for external binaries — Node, Engram, Graphify, Spec-Kit (`cli/src/engine/deps.ts`).
`copyTemplate` writes files and returns. So after `cortex init`, `.opencode/node_modules`
does not exist and the three tools that `import { tool } from "@opencode-ai/plugin"` have an
unresolvable import until the first worktree is provisioned.

This change makes the gap visible rather than silent — the old code skipped installing
whenever a lockfile was absent — but it does not close it. Closing it means deciding whether
`cortex init` should install, or whether the tools should not depend on a project-local
install. That is a scope decision, not a defect fix, and it is not covered here.

Related: `deps.ts` still treats **Spec-Kit as required**, which the `spec-kit-decommission`
handoff owns.

provisioning with no pinned fallback. Accepted in D01 with the reasoning recorded there. If it
ever bites, the remedy is to resolve the plugin version from the installed runtime.
